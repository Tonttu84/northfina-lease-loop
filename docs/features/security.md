# Security: demo mode, the response headers, the signed session, the public audit log, limits, strict bodies, no raw SQL

## What it does

Names the demo mode and switches it as one thing, puts the usual security headers on every response, signs the actor cookie so it cannot be written by hand, keeps a visitor's personal data out of the public audit log, caps what one client may write, and tests that every request body refuses unknown keys and that app code runs no raw SQL. None of it is the login itself, which is the sign-in link ([accounts.md](accounts.md), D93); while the demo tools are on, the "continue as" picker (D17) is the demo's shortcut, and the policy in [authorization.md](authorization.md) decides what each actor may do. Every security feature of the app, this page's and the others', is summed up with its threat, its test and a one-minute demo in [the security overview](../security-overview.md).

## The rule

**Demo mode (D74).** `DEMO_TOOLS` is the one switch: left empty, the demo tools are on in development and in the tests and off in a production build (`next start`); `1` turns them on there too, `0` turns them off everywhere. The tools are the scenario-card runner (`POST /api/demo/cards/[id]/run`), the demo clock's route (`POST /api/demo/clock`) and the clock cookie itself: with the tools off both routes answer 404 and `todayForRequest()` ignores the cookie, so a quote's validity, a signing link's expiry and the age at signing run on the real day. The demo page says when the tools are off and shows neither the clock form nor the Run buttons; the audit log stays, it is not a demo tool. The actor picker is a demo tool too since D93: `POST /api/actor` answers 404 and the header hides the picker while the tools are off, because the sign-in link ([accounts.md](accounts.md)) is the way in; `DELETE /api/actor`, the sign-out, always answers. The sign-in links' demo outbox is one too since D94: with the tools off `POST /api/login` answers without the link and keeps no token in clear, and neither the demo page's outbox nor the link on the sign-in and account pages is shown ([accounts.md](accounts.md)). A `.env` created before this change still says `DEMO_TOOLS="1"` (`ensure-env.mjs` never rewrites an existing file), so an older checkout keeps the tools on under `next start` until that line is emptied; the README says so. The header banner and the admin access code of the review's S1 are not in this slice.

**Headers.** Every response carries `Content-Security-Policy` (scripts, styles, fonts, images and connections from this origin only; Next's inline bootstrap needs `'unsafe-inline'`, development also `'unsafe-eval'`; no framing, `base-uri` and `form-action` here, no plugins), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin` and a `Permissions-Policy` that turns the camera, microphone, geolocation and payment APIs off. A production build adds `Strict-Transport-Security`. The signing page (`/[locale]/sign/[token]`) sends no referrer at all: its token is in the URL. The policy is static because the app loads nothing from a third party (`next/font` serves the fonts from here).

**Cookies.** The actor and demo-clock cookies are `HttpOnly; SameSite=Lax` always and `Secure` on a production build (`secureFlag`), never on plain-http development.

**The signed session (D92).** The actor cookie's value is `base64url(actor).expires.signature`: the actor, the unix second the session ends (30 days after it was set, the cookie's Max-Age) and an HMAC-SHA256 of the two under `SESSION_SECRET`, base64url. `scripts/ensure-env.mjs` writes a fresh 32-byte secret into `.env` the way it writes the audit key (`npm run db:setup`, `npm run dev`), the tests get one per run from `vitest.config.ts`, and the repository never holds one. `readActor` verifies before it trusts: a value nobody signed (the plain `admin` of a cookie from before this change), a signature that does not match (held to its 43-character spelling, then compared in constant time), an expiry on or before now, an empty actor or a missing secret all read as `anonymous`; what verifies is then checked against the customers as before. `POST /api/actor` checks the picker's plain id against the database and signs it (`resolveKnownActor`, then `actorCookieHeader`); the card runner sets the same cookie. Changing the secret signs everyone out; a secret shorter than 32 characters counts as missing. `npm start` runs `ensure-env.mjs` first (`prestart`), as `npm run dev` and the browser tests' server do, so a `.env` from before this change gets its secret on the next start; a bare `next start` on such a `.env` has none, every visitor reads as `anonymous` and `POST /api/actor` answers 500 until `npm run db:setup` adds one. A secret typed in by hand that is shorter than 32 characters is kept by the script, which warns, and treated as none by the app. A variable the process environment provides is never written to `.env`, and with both `SESSION_SECRET` and `AUDIT_SIGNING_KEY` provided the script creates no `.env` at all, so such a deployment needs no `.env` and no writable directory; a short value from the environment is reported like a short line in the file. Worked example: `YWRtaW4.1800000060.<43 chars>` verified at second 1 800 000 000 is `admin` for another 60 seconds; the same value with `admin` swapped for a customer id, or with the expiry pushed back, fails the signature and is nobody.

**The public audit log.** The chain stores every detail, so the hash holds and the admin reads the stored rows. Anyone else, on the audit page and from `GET /api/audit-log`, gets a copy with the personal fields masked as `•••`: the keys the apply form and the signatory list took from a person and the values derived from them (`birthDate`, `eighteenOn`, `monthlyNetIncomeCents`, `incomeCents`, `maxRentCents`, `revenueCents`, `businessId`, `country`, `email`, `signatoryEmail`, `signingLinkTo`), wherever they sit in the details; any string that reads as an e-mail address whatever its key (the signatory's `by`, while an actor id under the same key stays); and a signatory's e-mail in the actor column (`signatory:•••`). The ids stay: `cust-aino` names a demo customer, not a person.

**Cross-site writes.** A browser names where a request came from in `Sec-Fetch-Site`; the proxy refuses a write on `/api` (anything but GET, HEAD, OPTIONS) that says `cross-site` with 403 `CROSS_SITE`, before the limit counts it. A JSON body does not force a preflight here: `readJsonBody` never checks `Content-Type`, so another site can post a `text/plain` body that parses as JSON. What stops a cross-site write is the session cookie's `SameSite=Lax` together with this check, which also closes `POST /api/login/[token]`, a write with no body that opens a sign-in link and sets the session cookie (D93). A request without the header (a script, the tests) is not refused on it; `same-origin`, `same-site` and `none` pass.

**Limits.** The proxy counts the writes (anything but GET, HEAD, OPTIONS) on `/api` per client, the first address of `X-Forwarded-For`, which Next's server fills from the socket when a request carries none, so each address has its own window: at most 120 in a minute, then 429 `RATE_LIMITED` in the API envelope with `Retry-After`. Reads are not counted; one instance holds the one SQLite file, so one memory is the whole truth, and the map never holds more than 10 000 clients (the ended windows go first, then the oldest). It is a nuisance bar against a careless script, not a guarantee: a client that sets the header picks its own bucket. A body over 64 KiB is refused with 413 `PAYLOAD_TOO_LARGE`: before it is read when its declared length says so, once read when it declared none (a chunked body), in `readJsonBody` and the assessment route's own reader; the route handlers themselves put no limit on a body.

**Strict bodies and no raw SQL (issue 17).** Every request body is the `body` schema of its row in the route table (`src/server/routes.ts`), and `tests/meta-rules.test.ts` holds it there. It walks each body schema's Zod definition: an object counts as strict only when its `catchall` is `z.never()`, which is what `z.strictObject()` and `.strict()` set in Zod 4; `z.object()` (unknown keys dropped), `z.looseObject()`, `.passthrough()` and a `catchall` of anything else fail, at any depth, through `optional`, `nullable`, `default`, arrays, unions, pipes and lazies. A `z.record` counts as loose when its keys may be any string, and an unknown Zod type fails rather than passes. A second test follows every `readJsonBody(request, schema)` and `schema.parse(body)` in a `route.ts` back to the very schema of its row, so a route cannot parse a body the table does not declare. A third fails on `$queryRaw`, `$executeRaw`, `$runCommandRaw`, any `…Unsafe` method or `Prisma.raw(` in code under `src/` outside tests; comment lines and the tamper demo under `scripts/` are left out.

**Secrets.** The pre-commit hook already scans the staged files; `npm run check:secrets` (in `check:all`, so in CI) scans the whole tree with the same rules, `.secretlintignore` leaving out dependencies, build output, generated code and the local databases.

**Supply chain (D96).** Every `uses:` in `.github/workflows/ci.yml` names a full 40-character commit SHA, with the release tag that pointed at it in a trailing comment (`actions/checkout@3d3c42e… # v7.0.1`); Dependabot's weekly grouped GitHub Actions update moves the SHA and the comment together. `.npmrc` no longer turns audit off, so `npm ci` reports known advisories, and CI's "Dependency audit" step right after it, `npm audit --audit-level=high`, fails the run on a high or critical one. Moderate and low ones pass and wait for Dependabot: on 2026-11-10, ten moderate, all one advisory (`minimatch`, GHSA-g3hv-75wg-m249) through eslint and typescript-eslint, development only; `npm audit --omit=dev` finds none. `npm audit`'s only offered fix downgrades eslint a major; an `overrides` entry to `minimatch` 11.0.1 or later would clear it, but that is outside the `^10` range eslint 10 and its parts declare and untested against them, so for a dev-only moderate advisory it was considered and left.

## Decisions

- D74: `DEMO_TOOLS` now gates the clock as well as the card runner, and the default follows the build. The D74 row in `docs/decisions.md` is unchanged; this page is the record.
- D17 and D93: the picker hands out any actor while the demo tools are on; with them off, only the sign-in link does ([accounts.md](accounts.md)). The signed cookie (D92) and the link together close the polish review's security finding 1 (`docs/reviews/polish-2026-11-08.md`).
- D92: the actor cookie is a signed, expiring session; `SESSION_SECRET` from `.env`.
- D96: actions pinned by commit SHA, and CI fails on a high or critical `npm audit` finding.
- D97: the strict-body and raw-SQL meta tests: the bodies from the route table, strict read from Zod's own definition, raw SQL by a line scan of `src/`.

## Pure functions

- `demoToolsOn(env)` (`src/server/demo-tools.ts`): the switch, from the environment passed in.
- `secureFlag(env)` (`src/server/cookie-flags.ts`): `; Secure` on a production build, else nothing.
- `signSession({ actor, expiresAt }, secret)`, `verifySession(value, secret, nowSeconds)`, `newSession(actor, nowSeconds)`, `sessionSecret(env)` (`src/server/session.ts`): the signed session; the clock and the secret are arguments.
- `redactAuditDetails(details)`, `redactAuditActor(actor)`, `redactAuditEntry(entry)` (`src/domain/audit/redact.ts`): the visitor's copy of an audit row.
- `isCrossSite(request)` (`src/proxy.ts`): the `Sec-Fetch-Site` check.
- `createRateLimiter(rule)` (`src/server/rate-limit.ts`): `take(key, now)` says whether one more request of `key` fits the window; the clock is an argument.
- `assertBodySize(request, maxBytes)` (`src/server/api-response.ts`): 413 over the cap.
- `resolveToday(systemToday, override)` (`src/server/demo-clock.ts`): unchanged; the caller passes no override while the tools are off.

## Open questions

- A nonce-based policy (no `'unsafe-inline'` for scripts) needs the proxy to mint a nonce per request and thread it into every script tag; not needed while no third-party script and no user-written HTML is rendered.
- The `Permissions-Policy` list is the common four; extend it if a browser warns about another feature the app does not use.
- The mask is by key name plus the shape of an e-mail address: a new detail that carries other personal data under a new key must be added to `PRIVATE_DETAIL_KEYS`, or better, written under one of them. A value derived from a masked one (a date or an amount computed from it) needs its own key in the list, as `eighteenOn` and `maxRentCents` do.
- The limit trusts the first `X-Forwarded-For` address, which the client can set (Next keeps a value the request brings); a real deployment keys on the reverse proxy's own header (`CF-Connecting-IP`, `X-Real-IP`) and strips the client's.
- The mask holds against casual readers and crawlers: while the demo tools are on, the admin's view is one picker click away (D17), by design; with them off, it takes the back office account's sign-in link (D93).
- A session is not revocable before its expiry except by changing the secret, which signs everyone out; a server-side list of revoked sessions is the next step if one person's session must be ended.
- The session's expiry is in real seconds, not on the demo clock: a judge travelling to 2028 stays signed in.
- A production build served over plain http on a LAN address (the `Network:` line `next start` prints) gets no actor or clock cookie back: the browser drops a `Secure` cookie there. `localhost` counts as secure, https always does; a demo shown from another machine on the LAN needs https (or a tunnel) on a production build, or `next dev`.
